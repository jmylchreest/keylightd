# Keylightd Control GNOME Extension

This directory contains a GNOME Shell extension for controlling Key Lights via the keylightd HTTP API.

## Features
- Integrates with GNOME quick settings
- Control individual lights and groups
- Configure API endpoint and authentication key via UI
- About page showing version and commit information
- Automatic version embedding via GitHub workflows
- Follows GNOME extension best practices for structure and packaging

## Development & Packaging

1. **Update version information (optional - done automatically by Makefile):**
   ```sh
   make version-info
   ```
   Or run the script directly:
   ```sh
   ./update-version-info.sh
   ```

2. **Build the extension:**
   ```sh
   make build
   ```
   This automatically generates version info and runs tests (no manual schema compilation needed for GNOME Shell 45+).

3. **Package the extension:**
   ```sh
   make pack
   ```
   This uses `gnome-extensions pack` and outputs a zip in `../../dist/gnome-extension/`.

4. **Create zip (alternative to pack):**
   ```sh
   make zip
   ```

5. **Test the implementation:**
   ```sh
   make test
   ```

6. **Run tests:**
   ```sh
   make test
   ```
   Or run specific test types:
   ```sh
   cd tests
   ./run-tests.sh unit        # Fast validation tests (default)
   ./run-tests.sh integration # Full build and packaging tests
   ./run-tests.sh all         # All tests
   ```

## Installation & Testing

1. **Install the packed extension:**
   ```sh
   gnome-extensions install --force dist/gnome-extension/keylightd-control@jmylchreest.github.io.shell-extension.zip
   ```
   Or copy the folder to your local extensions directory:
   ```sh
   cp -r contrib/gnome-extension/keylightd-control@jmylchreest.github.io ~/.local/share/gnome-shell/extensions/
   ```
2. **Enable the extension:**
   ```sh
   gnome-extensions enable keylightd-control@jmylchreest.github.io
   ```
3. **Reload GNOME Shell:** (Alt+F2, type 'r', press Enter)
4. **Configure:** Click the icon in the quick settings menu and set the API endpoint and key.

> **Note:** If the API key is not set, the extension will not attempt to interact with the API and will only show the configuration UI.

## GNOME extension review guidelines

GNOME publishes the rules reviewers apply to extensions.gnome.org submissions
and a companion guide with coding examples. See the
[GNOME Shell Extensions Review Guidelines](https://gjs.guide/extensions/review-guidelines/review-guidelines.html)
and [GNOME Extension Best Practices](https://gjs.guide/extensions/review-guidelines/best-practices.html).

- **Use the libraries selected by the host.** In shipped extension code, import
  `gi://Gdk` and `gi://Soup` without a `?version=` suffix. The Shell and its
  preferences service select the library versions for their processes. Our
  import check covers both paths. [Keylightd Control review 9](https://extensions.gnome.org/review/79155)
- **Keep the two UI toolkits in their own processes.** Use `St` for Shell UI
  and `Gtk`, `Gdk` and `Adw` for preferences. A shared module such as
  `transport.js` must be safe to import from both entry points.
- **Give each asynchronous resource an owner.** Keep the `Soup.Session` where
  the extension can call `abort()` on disable, or the preferences window can
  call it on teardown. This cancels pending requests and closes idle
  connections. Completion handlers must also tolerate the window closing before
  they run. Apply the same ownership rule to timers and signal handlers.
  [Soup.Session.abort()](https://libsoup.gnome.org/libsoup-3.0/method.Session.abort.html)

Run `make test` from this directory to check imports. When changing asynchronous
code, start a request and close Preferences or disable the extension while it
is pending. Reopen or re-enable it and check that the next request succeeds.

## Debugging

### Reproducible GNOME 48–51 Wayland Tests

From the repository root, run:

```sh
make -C contrib/gnome-extension test-gnome-all
# Or select one release (the default is 51):
GNOME_VERSION=48 make -C contrib/gnome-extension test-gnome
```

This requires Linux x86-64 and Podman. To use Docker, set
`CONTAINER_RUNTIME=docker`. The first build downloads roughly 400–500 MiB of
packages per release; subsequent builds reuse each runtime layer. No local GNOME
installation is needed. The `test-gnome51` target remains available as a shortcut.

The [Containerfile](tests/gnome-shell/Containerfile) pins the Arch base image by
digest and installs packages from a dated Arch archive snapshot. It checks
that the installed Shell matches the selected major version. Each run prints the Shell, Mutter, GJS
and Mesa package versions and starts a fresh headless Wayland compositor with
Mesa software rendering and a 1600×1200 virtual monitor. Both D-Bus buses and all
settings live inside the container. The test has no network access, host mounts,
display sockets or GPU devices, and does not require privileged mode.

| GNOME Shell | Arch archive snapshot |
| --- | --- |
| 48 | 2025-08-01 |
| 49 | 2026-02-01 |
| 50 | 2026-08-01 |
| 51 | 2026-10-28 |

The container loads the extension with normal version validation, then a test
extension checks menu orientation, constructs light and group controls including
their sliders, and disables and re-enables the extension. A failure or timeout
returns a nonzero exit code and prints the session log. Missing desktop services
such as GDM or the calendar service can produce unrelated warnings in that log.
This tests real Shell widgets and the extension lifecycle; it does not test
physical lights or a real daemon. A container-local HTTP fixture supplies a
Studio group and two lights with different power states.

Screenshots and logs are copied to a new `dist/gnome<version>-*` directory on every run,
including failed runs. Captures cover quick settings, the expanded light/group
menu, all five preferences pages, add/edit/delete group dialogs and the log-level
dropdown. CI runs a four-version matrix and uploads a separate
`gnome<version>-ui-*` artifact for each version, retained for seven days.
Release packaging waits for all four UI tests to pass. The screenshots are for
visual review, not pixel-by-pixel golden tests.

For an older checkout whose metadata does not list GNOME 51, the test runner also
accepts `--allow-unsupported`. This bypasses version validation only in the
container, reproducing the manual metadata workaround in
[issue #56](https://github.com/jmylchreest/keylightd/issues/56):

```sh
contrib/gnome-extension/tests/test-gnome-shell.sh --allow-unsupported
```

The original code fails with `No property vertical on StBoxLayout`. GNOME 51
removed that property; the extension now uses `Clutter.Orientation` for all four
affected layouts, as described in the
[GNOME 51 porting guide](https://gjs.guide/extensions/upgrading/gnome-shell-51.html).

### Publishing to extensions.gnome.org

One extension ZIP supports GNOME 48, 49, 50 and 51 through the `shell-version`
list in `metadata.json`. A separate ZIP per Shell version is unnecessary while
the same implementation works on all four. See GNOME's
[multi-version support guide](https://gjs.guide/extensions/development/targeting-older-gnome.html).

EGO also supports multiple uploaded versions under the same extension UUID.
If incompatible changes eventually require a legacy branch, publish separate
ZIPs with accurate, preferably non-overlapping `shell-version` lists. GNOME's
[45 migration announcement](https://blogs.gnome.org/shell-dev/2023/09/02/extensions-in-gnome-45/)
describes this approach for maintaining pre-45 and post-45 releases. Keep the
older compatible release active while its users still need it.

Stable releases with extension changes upload the already-built release ZIP
using `gnome-extensions upload` from the pinned container runtime. This replaces
the third-party upload action and avoids depending on the runner's GNOME CLI.
Set repository secrets `EGO_USERNAME` and `EGO_PASSWORD` for the owning EGO
account. The password is passed over stdin to `--password-file=-`.

To upload an existing bundle manually from the command line:

```sh
export EGO_USERNAME=your-account
read -rs EGO_PASSWORD
export EGO_PASSWORD
contrib/gnome-extension/publish.sh dist/gnome-extension/keylightd-control@jmylchreest.github.io.shell-extension.zip
unset EGO_PASSWORD
```

#### Republish an extension-only fix

After the workflow is merged into `main`, open **Actions → Publish GNOME
extension → Run workflow**. Select the branch containing the fix and click
**Run workflow**. To submit the current commit on `main`, run

```sh
gh workflow run publish-gnome-extension.yml --ref main
```

The workflow tests the selected commit on the GNOME Shell matrix, packages
the extension, saves the ZIP as a workflow artifact and submits it for review
using the same EGO credentials as a stable release. A failed upload fails the
run. The About page records the existing keylightd release version from the
nearest stable tag and the commit containing the fix. This path creates no
Git tag or GitHub release. The **Build Release** workflow also offers an
extension upload, but a manual snapshot run creates a GitHub prerelease.

Keep the extension UUID. EGO assigns each upload a new submission number, so
a correction to version 9 gets a new review under the same listing. There is
no version field to bump by hand. The upload script accepts the EGO submission
terms. [GNOME extension version metadata](https://gjs.guide/extensions/overview/anatomy.html#version)

### Testing in a Nested Wayland Session (Recommended)

Running GNOME Shell in a nested Wayland session allows you to test and debug your extension without affecting your main desktop session.

1. **Start a nested GNOME Shell session:**
   ```sh
   dbus-run-session -- gnome-shell --devkit
   ```
   This opens a development (devkit) GNOME Shell instance inside your current session (recommended for GNOME Shell 49+). For older shells (<49) you can still use: dbus-run-session -- gnome-shell --nested --wayland

2. **Install and enable your extension inside the nested session:**
   - Open a terminal inside the nested session (e.g., with `Ctrl+Alt+T` or from the app grid).
   - Install the extension as described above.
   - Use `gnome-extensions` commands inside the nested session to enable/disable and debug.

3. **View logs for debugging:**
   - Run `journalctl -f /usr/bin/gnome-shell` in a terminal to see GNOME Shell logs in real time.
   - Use `gnome-extensions info keylightd-control@jmylchreest.github.io` for extension status.

### Quick Reload (X11 only)
- On X11, you can reload GNOME Shell with `Alt+F2`, type `r`, and press Enter.
- On Wayland, you must log out and back in, or use a nested session as above.

### General Tips
- Use the [Looking Glass](https://wiki.gnome.org/Projects/GnomeShell/LookingGlass) debugger (`lg` in Alt+F2) for live JS console and object inspection.
- Use `console.log()` and `console.error()` in your JS code for debugging output.
- Always test with both the preferences dialog and the quick settings menu.

The Connection tab supports a manual API address and key, a local Unix socket, and paired HTTPS. The socket and pairing methods use the matching version of `keylightctl` on your PATH. Pairing stores the verified profile in `$XDG_CONFIG_HOME/keylightd/gnome-pairing.json`.
